# Git 推送前代码审查实施方案

> 修订日期：2026-11-13。
>
> 文档状态：待实施。本次仅修订方案文档，不恢复代码、不安装 hook、不运行前置验证、不启动模型审查。

## 一、目标与实施原则

本方案从最初的 Nuxt 空项目重新建立本地自动审查，再逐阶段实现 Git 推送前审查门禁，不在当前 CI 改造基础上继续抽取或复用实现。

已确定：

- 恢复基线：`a0a8fd8`，最初的 Nuxt 空项目，无组件编写示例。
- 本地审查：在空项目上重新补入，不继承当前 CI 改造。
- 首批客户端：Windows 原生 Git、VS Code、Codex 桌面端。
- 优先操作方式：通过 VS Code、Codex 内置 Git 界面发起推送；命令终端使用同一套门禁。
- 推进方式：先验证前置条件，每个阶段单独安排，交付结果后停止，不自动进入下一阶段。

最终门禁要求：

- 待推送的固定提交已经过有效审查，或命中完全匹配的有效审查缓存。
- Standards 和五条 AI 规则完成必要审查，执行证据和结果有效。
- 当前及历史 Critical、Major 均已确认修复；Minor 不阻断。
- 审查失败、超时、取消、证据不足、修复状态无法确认或完整报告生成失败时阻断。
- 过程简短，最终问题完整，并提供 HTML、Markdown、JSON 报告。

“本地任务完成后自动审查”与“推送前强制门禁”是两种不同能力。前者恢复完成，不表示后者已经实现。

本地 hook 可被 `--no-verify`、更改配置或其他推送实现绕过。远端合并门禁在后续独立阶段建设，不承诺服务器拒收所有未经审查的分支提交。

## 二、必须先完成的前置验证

前置验证在隔离测试仓库和本地测试远端进行，不修改当前项目，不先恢复基线。先用确定性脚本模拟通过、阻断及进度输出，排除模型耗时和不确定性的干扰。

下面均为待开展的验证项目，不代表本次已执行。初始状态统一为“未验证”，验证结果只使用“已验证、失败、未验证”。

### A. 客户端是否执行 hook、是否真正阻断

| 验证入口 | 必须确认 | 初始状态 |
| --- | --- | --- |
| PowerShell、Git Bash | `pre-push` 被调用；非零退出码阻止远端 ref 更新 | 未验证 |
| VS Code 推送按钮 | 是否执行 hook、失败是否可见、远端是否未更新 | 未验证 |
| VS Code 同步按钮 | 拉取与推送阶段如何呈现；推送被阻断时提示是否明确 | 未验证 |
| Codex 内置 Git 推送按钮 | 是否执行 hook、是否等待、如何显示错误和报告路径 | 未验证 |
| Codex 命令工具执行 `git push` | hook 输出、退出码、取消传播是否正确 | 未验证 |

每个入口分别测试成功和失败，记录客户端版本、操作步骤、hook 日志、退出码以及远端 ref。界面不提供进程退出码时，记录 hook 自身退出码、界面结果和远端状态，不推测客户端内部状态。

不能用命令工具的测试结果替代内置按钮验收。若某个按钮不执行 hook，记录为不满足目标并停止该入口的后续集成；使用内置终端只能作为替代方式，不能标记按钮已支持。

### B. 过程和结果是否可见

验证以下输出：

- 短过程：启动、阶段变化、任务完成数。
- 完整结果：全部模拟问题、阻断原因、报告绝对路径。
- 中文、空格路径、长报告及日志截断情况。
- Windows 无 TTY 调用能否打开独立进度终端。
- 关闭展示窗口是否影响原 Git 操作。
- 无法打开窗口时，调用方日志是否仍能交付结果。

确定性探针必须标注“兼容性测试”，不得显示模拟的“真实审查通过”。窗口中的结论必须区分审查判定与实际 Git 推送结果。

### C. 长时间执行与取消

先短时测试，再对支持入口验证接近计划审查预算的等待行为：

- 客户端是否提前超时或终止 hook。
- 持续输出能否保持可见。
- 原 Git 操作取消后，模拟子进程是否停止。
- 展示窗口关闭后，审查是否仍由原 hook 控制。
- 是否出现重复启动、孤儿进程或错误放行。

若客户端无法等待完整审查，可评估“先独立审查，再由界面推送校验缓存”。这属于体验调整，须单独确认，不能自动替代原目标，也不能为了适配超时而降低审查要求。

### D. 本地审查执行能力

客户端兼容性通过后，再单独安排 AI 能力验证：

- 本机 Git、Node、Codex CLI 的实际版本和启动路径。
- 图形界面进程的 PATH、凭据访问与非交互执行能力。
- 独立审查会话是否可以启动。
- 六路独立 worker 是否可用，容量不足时能否保留独立任务并调度。
- 固定提交材料是否完整、是否排除未提交内容。
- 只读源码、临时目录写入权限是否实际有效。
- worker 终态、输出和执行证据能否可靠采集。
- 超时、取消、缺凭据、调用失败是否可靠返回失败。

不继承当前 CI 固定版本作为新方案的既定要求。先验证本地可用版本，再将通过验收的版本固定到新实现中；hook 不自动升级或降级。

真实模型调用与确定性兼容性测试分开，不在首轮客户端验证中启动付费审查。版本查询、配置查询或历史 CI 成功记录，均不能替代本地隔离、六路执行和证据验收。

### E. 安装与状态管理条件

还需验证：

- 现有 `core.hooksPath` 和已有 hooks 是否冲突。
- 多 worktree 是否能定位同一可信安装。
- 隔离快照、私有运行材料和公开报告的路径是否可用。
- 多次推送的锁、取消后状态恢复是否可实现。
- 成功报告及历史问题账本如何持久保存。
- 如何防止待审分支修改本次审查工具与门禁规则。

安装、路径和权限问题在恢复前完成基础可行性检查；具体锁、缓存和账本机制在对应实施阶段验收，不能把目录可写当作完整状态管理已经通过。

任何关键条件失败，都先提交原因、影响及调整建议，不继续实施完整门禁。

### 前置验证交付格式

每项记录：验证 ID、客户端及版本、操作入口、测试条件、实际步骤、预期结果、实际结果、hook 日志、退出码或可用状态、远端 ref、报告位置、结论及阻塞项。

兼容性探针及材料保存在隔离测试目录，不安装到日常仓库。对图形界面的成功、失败及输出结果保留实际截图或录屏；无法操作的入口保持“未验证”。

## 三、恢复基线与重建边界

`a0a8fd8` 没有组件示例，也没有本地自动审查配置，因此恢复拆成两个独立步骤：

1. 恢复该提交的项目文件状态，移除后来增加的组件示例、CI 审查工作流、适配脚本及验收示例。
2. 在空项目上重新建立中文协作规范、本地自动审查触发规则、审查 skill 和必要 helper。

历史提交 `becd98d` 中的本地审查规则、Standards 和五条 AI 规则可作为来源参考，但必须逐项核对，只引入本地审查所需内容。不复制其 PR 工作流，也不从当前实现抽取 CI 模块。

恢复通过新分支及可审查提交完成，保留 Git 历史和本方案文档，不使用破坏性重置。恢复阶段前核对工作区，保留其他未提交改动；无法安全分离时先报告，不覆盖。

恢复空项目的验收标准：

- 页面恢复 Nuxt 初始欢迎页。
- 不存在弹窗、Tabs 等组件编写示例。
- 不存在后来引入的 CI 审查链路。
- 项目基线相对 `a0a8fd8` 的差异仅为明确保留的方案文档及经核对保留的用户改动，全部列明。

随后重建本地自动审查时，规则和所需 skill 必须单独可识别，不能把整个历史版本直接复制回来。该阶段验收本地审查，不安装推送门禁。

## 四、分阶段实施路线

| 阶段 | 工作范围 | 交付物及停止点 |
| --- | --- | --- |
| 0A：客户端兼容性 | 仅确定性 hook 探针、输出窗口、阻断和取消验证；完成安装环境基础检查 | 客户端支持矩阵、证据和阻塞项；完成后停止 |
| 0B：本地 AI 能力 | 单独验证执行器、六路任务、隔离、证据与失败处理 | 可行性报告、版本建议和阻塞项；完成后停止 |
| 1：恢复空项目 | 恢复 `a0a8fd8` 文件基线，清除后续改造及组件示例 | 基线 diff 和核对清单；完成后停止 |
| 2：重建本地自动审查 | 重新引入本地规则、skill、材料构建和完整报告 | 本地自动审查验收；不安装推送门禁；完成后停止 |
| 3：推送门禁最小实现 | 固定待推送提交、同步审查、Critical/Major 阻断、双层输出 | 命令行与已验证图形入口验收；完成后停止 |
| 4：完整状态管理 | 历史问题复核、严格缓存、多 ref、锁和 worktree | 防漏检、并发和故障验收；完成后停止 |
| 5：远端合并兜底 | 从新基线另行设计必要的远端检查与分支保护 | 单独方案和验收，不恢复现有 CI 实现作为捷径 |

阶段 3 仅为最小实现，历史问题和缓存等阶段 4 能力未完成前，不宣称全部目标达成。

每阶段的开始条件是上一阶段结果已被确认，以及本阶段已被单独安排。前置条件通过不构成连续执行后续阶段的授权。失败或未验证项目需要明确处理，不自动更换目标、减少规则或采用宽松模式继续。

## 五、后续实现必须保留的行为约束

以下为分阶段实现的最终要求，不表示本次立即建设，也不预先指定当前 CI 实现为技术来源。

### 5.1 推送门禁

```text
VS Code / Codex Git 界面 / 命令终端发起推送
  → pre-push 接收全部待推送 ref 和固定 SHA
  → 检查环境、可信工具和审查范围
  → 检查完全匹配的有效缓存，或同步执行审查
  → 复核历史 Critical/Major
  → 校验结果与执行证据
  → 生成完整报告
  → 放行则继续 Git 推送，否则非零退出阻断
```

- hook 同步等待，不允许后台启动审查后立即返回成功。
- 审查固定待推送提交，不默认使用当前 `HEAD`，不混入工作区未提交内容。
- 默认审查完整分支差异并复核历史问题；具体基线映射在推送门禁阶段设计与验收。
- 历史问题只有明确修复证据才关闭。未再次提及、行号变化或用户勾选“已处理”不能自动关闭。
- 缓存必须绑定仓库、分支、目标、固定提交、可信工具、规则、模型配置、历史账本及完整报告；失败结果不能作为放行缓存。
- 多 ref、并发和 worktree 完整支持在阶段 4 交付；阶段 3 未支持的操作应明确拒绝，不静默跳过。
- 未经单独要求，hook 不修复代码、不创建提交、不自动重推。

### 5.2 双层输出与呈现

第一层为简短过程，显示启动、阶段变化及真实任务完成数量，不输出模型推理或原始会话日志。

第二层为完整结果，包含审查范围、任务状态、全部核实问题、Critical/Major/Minor 数量、触发条件、影响、历史问题复核、阻断原因和完整报告绝对路径，不设置固定问题数量上限。

```text
[代码审查] 已固定待推送提交 a1b2c3d
[代码审查] 已完成 4/6
[代码审查] 正在复核历史阻断问题

代码审查完成：推送已阻止
Critical 0 · Major 1 · Minor 2

[Major] 登录失败后仍跳转首页
位置：app/pages/login.vue:48（固定 head）
触发：登录接口返回业务失败
影响：用户进入首页后无法访问受保护数据

完整报告：<绝对路径>/report.html
```

交互式命令行优先在原终端展示。图形入口和无 TTY 调用优先打开独立进度终端，原调用方同步接收日志和退出码。展示窗口仅观察，不启动第二次审查，不负责放行；关闭窗口不得绕过门禁。

窗口显示“允许继续推送”，不显示“推送成功”；后者由 Git 实际结果决定。窗口不可用时保留日志与报告交付，并明确说明展示问题。

报告提供 HTML、Markdown、JSON，过程日志与最终结果一并保存。具体路径和保留策略在本地报告实现阶段明确。输出应支持中文、空格路径和长报告，防止终端控制字符、HTML 或 shell 内容被解释执行。

### 5.3 失败与远端边界

审查未完成与存在阻断问题分别报告，不能把“执行完成”视为“允许推送”。已有问题应保留，失败时不能显示“未发现问题”。

真实推送还可能因网络、权限或非快进失败，审查通过不保证推送成功。

本地 hook 的可绕过边界必须在使用文档中明确。远端检查与分支保护在阶段 5 单独设计、配置和验收，不继承现有工作流或历史成功结果作为已完成证明。

## 六、阶段验收与完成定义

每阶段报告必须区分“已实现”“已验证”“失败”“未验证”，列明下一阶段仍需满足的条件。

| 目标 | 最终验收要求 |
| --- | --- |
| 未审查阻断 | 无有效报告或缓存时必须审查，完成前远端 ref 不更新 |
| 问题阻断 | 当前及历史 Critical/Major 未确认修复均阻断，明确修复后才能放行 |
| 故障阻断 | 超时、取消、缺凭据、调用失败、证据不足、完整报告写入失败均阻断 |
| 图形界面 | VS Code、Codex 内置按钮分别实际验证，不由终端测试推导 |
| 输出呈现 | 过程简短、结果完整、报告可访问；窗口关闭不影响门禁 |
| 范围与状态 | 固定提交不受工作区修改影响；多 ref、缓存、账本、锁及 worktree 不漏检 |
| 远端兜底 | 绕过本地后，受保护分支仍受独立合并检查约束 |

原生按钮未通过实测、本地执行能力不足、完整状态管理未完成或远端保护未配置时，不宣称整体目标完成。

当前全部前置验证及实施阶段均未开展。本次只修订本文档；真正开展验证时，首先仅安排阶段 0A，交付结果后停止。
